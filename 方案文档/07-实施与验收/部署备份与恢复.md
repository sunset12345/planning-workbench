# 部署、备份与恢复

## 1. 运行目录职责

应用代码/构建产物与运行数据分离：SQLite、资源、原件、临时转换、日志、配置、备份各有独立目录。运行数据不放入前端 public 目录，不在应用重建时清空。首次启动检查路径权限、剩余空间、数据库版本和白名单格式。

本机先绑定回环地址；局域网开放需要单独配置监听、TLS、允许访问的网络、会话策略及备份路径。数据库文件只由服务器本地进程访问，不放共享网盘让多个客户端同时打开。浏览器通过 API 使用服务。

## 2. 启动与更新流程（需实现配套脚本）

1. 安装经过确认的运行环境与锁定依赖，记录版本。
2. 复制应用配置示例，设置本机数据目录；白名单认证配置经批准的安全流程初始化。
3. 初始化数据库并导入演示项目；检查运行模式标签，不混入真实数据。
4. 通过登录、保存、重启、附件下载自检后迁入真实资料。
5. 更新前做一致性备份，在副本测试数据迁移；再停写、更新、迁移、自检。
6. 更新失败回滚应用和匹配的数据备份，不用旧应用强行打开已不兼容的新数据库。

本文不提供未经实际构建验证的“一键启动命令”，实施交付时补上真实系统、版本、命令和日志位置。

## 3. 一致性备份

最小可靠方案：进入维护只读模式 → 等待所有保存/导入提交结束 → SQLite一致性快照 → 复制快照所引用的不可变资源/原件 → 生成带哈希manifest → 验证 → 退出维护模式。

SQLite可使用其备份机制生成数据库快照，不能假定在线复制单个 `.db` 文件就是一致性备份，尤其启用 WAL 时。[SQLite 官方备份文档](https://www.sqlite.org/backup.html)

备份范围：数据库、所有当前及历史引用资源、部署配置（敏感配置单独限制访问）、应用/schema版本、校验清单。会话不恢复为有效登录；认证文件若需备份，采用主机受限/加密备份流程，绝不放入普通项目导出包。

后续可改为不停机快照，但必须协调资源清理与数据库快照的时点；未实现前不要承诺热备无停写。

## 4. 建议策略

团队试用可先提议每日一次、重大导入及升级前额外备份，保留 7 个日备份和 4 个周备份；频率和保留量需负责人结合容量确定，本文不会创建计划任务或自动删除备份。仅备份到同一硬盘不足以防磁盘损坏；异盘/异机位置与权限另行确认。

RPO（可接受数据损失时长）和RTO（恢复耗时目标）由负责人设定；每日备份意味着极端情况下可能丢失最多近一天的新提交。项目导出是迁移工具，不等同完整服务备份。

## 5. 恢复演练

在独立空目录检查备份校验值 → 启动匹配版本应用 → 恢复数据库与资源 → 重新配置白名单/会话 → 验证项目数、文档数、资源引用、抽查历史和权限 → 记录耗时 → 负责人确认后再切换正式数据路径。

任何覆盖正式数据的恢复都需预先确认目标和保留旧数据副本；不得用测试恢复自动覆盖生产。演练合格后才能说“备份可恢复”，仅显示“复制完成”不算验证。

## 6. 运维可见性

展示可用磁盘空间、最近成功备份时间、失败任务数、服务版本与数据库版本。日志做轮转和容量限制；监测磁盘满、数据库忙、转换超时、备份失败。失败时告警文案准确，不把队列已接收写成已保存。
