## 1. 目标与实施顺序

建设一个供策划、开发、美术和测试共同使用的网站，支持**上传策划资料、关系图浏览、分类阅读、全文检索和在线编辑**。

整体参考示例图的“左侧关系图＋右侧内容卡片”，结合前面讨论的策划案规范组织内容。

已确定的实施顺序：

1. **先做可操作原型**，验证上传、阅读、检索和编辑体验。
2. 原型确认后，由项目负责人决定正式存储使用 **GitLab 或 Google**，再接入登录、权限和多人持久化。
3. 正式版支持 GitLab、Google 两种账号登录，按工作台项目权限访问；**保存成功后立即生效**。

存储选择是保留给项目负责人的阶段决策。第一阶段不接入正式存储，不同时开发两套同步系统。

## 2. 页面与核心交互

| 区域 | 功能与交互 |
| --- | --- |
| 顶部导航 | 项目切换、全局搜索、上传文件、新建策划案、保存状态、账号入口 |
| 左侧关系图 | 展示“项目→系统→功能”，支持缩放、拖动、展开收起、重置布局、只看当前关联 |
| 右侧分类卡片 | 按功能概述、规则、UI、配置、资源、验收等分类；显示摘要、所属功能和填写状态 |
| 内容详情 | 点击卡片进入完整图文，提供章节目录、关联内容、来源附件和编辑入口 |
| 编辑界面 | 支持标题、段落、列表、表格、图片和链接；提供保存、取消、未保存提示 |
| UI阅读视图 | UI示意图与对应控件说明并排展示，支持图片放大、页面切换和查看红点规则 |
| 搜索结果 | 检索标题、正文、配置字段和附件名称；显示命中片段，点击定位到具体章节 |

交互约定：

- 点击关系图节点，右侧切换到该系统或功能；点击卡片中的关联项，可以反向定位关系图。
- 提供完整文档阅读模式，支持收起关系图，方便连续阅读长文。
- 分类卡片与完整正文引用同一份内容，修改后同步刷新。
- 节点归属、依赖和引用关系由用户明确设置；导入时只根据标题生成章节结构，不自动推断业务依赖。
- 状态使用“已填写、无、待确认、后续补充”，显示缺少的规范章节；填写完整度不代表业务已经验收。
- 首版优先适配桌面浏览器，采用参考图的浅色背景、分类卡片和清晰的节点层级。

## 3. 文件上传与内容组织

### 3.1 文件支持

支持多文件上传，以及包含正文和图片的 ZIP 文件包。上传后先预览转换结果，再选择项目、系统和功能归属。

| 类型 | 首版处理方式 |
| --- | --- |
| Markdown | 转成可编辑正文，保留标题、列表、表格、链接及配套图片 |
| Word `.docx` | 转成可编辑正文，提取图片，同时保留原文件供下载 |
| Excel `.xlsx` | 提供工作表切换、单元格内容预览和原件下载；修改后上传替换 |
| PNG、JPG等图片 | 用于UI示意图和资源说明，支持关联到具体页面或章节 |
| XMind | 保存源文件，并允许上传配套预览图；首版不编辑XMind内部节点 |

Word转换以内容结构为主，不承诺保持原有分页与复杂排版。转换结果需列出未支持或可能变化的内容，避免静默丢失。可采用 [Mammoth](https://github.com/mwilliamson/mammoth.js) 完成基础转换。

具体规则：

- ZIP中的相对图片路径在导入后重建为工作台资源引用；缺失图片明确标记。
- 同名文件由用户选择“新增资料”或“替换已有资料”，不自动覆盖。
- Word转换后，网页正文成为后续编辑对象；原Word标记为“导入原件”，保留导入时间。
- Excel仅展示文件中保存的结果；没有可用结果的公式单元格显示公式及未计算状态，不重新执行公式。
- 不执行导入文件中的脚本、宏或嵌入程序；转换后的富文本经清理后展示。

### 3.2 内容结构

沿用统一策划案规范，提供以下分类：

**修订记录、思维导图、功能描述、配置字段、UI及交互、多语言、音效、美术资源、打点、验收、待确认事项。**

红点放在对应UI页面下。新建策划案直接生成模板；旧文档可先保持原章节结构，再由用户调整分类，不强制补齐后才能阅读。

最小数据对象为：项目、系统、功能、文档、章节、资源、关联关系、版本。章节和资源使用稳定标识，改标题后仍可保持卡片、关系图和引用位置的关联。

## 4. 技术结构与分期交付

### 4.1 第一阶段：可操作原型

- 使用 React、TypeScript、Vite 构建独立网页应用，关系图采用 [React Flow](https://reactflow.dev/learn)。
- 正文采用富文本编辑器，使用结构化内容作为内部编辑格式；原件与图片独立保存。
- 原型通过浏览器 IndexedDB 保存项目数据，支持导出和重新导入完整项目包。
- 搜索从已导入内容生成，可重新构建；无需接入外部搜索服务。
- 用现有装备文档验证功能层级，用同伴文档验证图文阅读，再补Word、Excel及XMind样例验证上传流程。
- 交付可运行原型、样例项目包、启动说明及验证记录。

原型数据保存在当前浏览器。跨设备共享、真实账号权限和多人保存留到第二阶段验收。

### 4.2 第二阶段：正式存储与团队访问

**启动条件：项目负责人确认GitLab或Google作为正式存储，并提供对应接入环境。**

前端通过统一存储接口读写资料，接口覆盖：读取项目、读取文档、保存版本、上传资源、查看历史和恢复版本。保存请求携带读取时的版本标识，返回实际保存的新版本。

- **选择GitLab时**：正文、项目结构、资源和原件保存到指定仓库；一次保存形成一次提交，记录修改人和摘要。GitLab提供文件及批量提交接口，可用于实现版本保存。参考 [GitLab Commits API](https://docs.gitlab.com/api/commits/)。
- **选择Google时**：接入方案在本阶段明确Google Drive文件存储与原生Docs的承载范围，再实现对应适配器；前端阅读、检索和编辑流程保持一致。
- 服务端处理存储授权、会话和权限；正式策划内容保存在所选平台，搜索索引可以重建。
- 登录使用官方授权跳转，提供“使用GitLab登录”和“使用Google登录”；管理员连接团队资料，成员无需同时拥有两种账号。参考 [GitLab OAuth](https://docs.gitlab.com/api/oauth2/) 与 [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)。
- 采用管理员、编辑者、阅读者三种项目角色；登录成功后仍需加入项目才能访问内容。
- 保存成功立即更新内容与搜索索引；其他在线读者收到更新提示。编辑中的页面不被远端更新直接替换。
- 两人修改同一版本时，后保存者收到冲突提示并保留自己的修改，比较最新内容后重新保存；恢复历史版本产生一条新版本记录。

### 4.3 第三阶段：团队试用与完善

选择一个系统进行真实协作试用，完成资料迁入、权限配置、部署与备份恢复验证，再逐步扩大使用范围。

AI问答、自动提取业务关系、实时共同编辑、批注讨论、GitLab与Google双向同步，作为后续扩展，不纳入首版交付。

## 5. 验收标准

- [ ] 能完成“上传文件→确认转换→归属功能→分类阅读→编辑保存→检索定位”的完整流程。
- [ ] 关系图、卡片和正文定位一致；修改一处后不会出现多份内容不一致。
- [ ] Word样例的标题、正文、图片和基础表格可读取；转换差异有提示，原件可下载。
- [ ] Markdown配套图片正确显示；缺失附件、损坏文件和不支持格式有明确反馈。
- [ ] Excel可切换工作表；XMind可下载源文件并查看已上传的预览图。
- [ ] 原型刷新后数据仍在，项目包导出再导入后，正文、资源和关系保持一致。
- [ ] 正式版两种登录方式都可进入被授权项目；阅读者不能修改，未授权成员不能通过搜索或附件链接访问资料。
- [ ] 保存失败不显示成功、不丢失当前修改；并发保存不静默覆盖；历史恢复可追溯。
- [ ] 首轮测试数据按100份文档、500个关系节点、600张图片准备，验证搜索、图谱切换和长文阅读；图片按需加载，图谱默认聚焦当前系统。
