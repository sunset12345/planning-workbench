# 工作台适配与导入规范

新建、完整整理或准备工作台导入时使用。目标是让同一份策划内容支持完整阅读、分类卡片和业务关系图。本文约定生成文件与未来导入器的交换格式，不表示工作台或导入器已经实现。

## 1. 归属与稳定标识

- 业务层级为项目 → 系统 → 功能。系统概述可归属系统，功能案归属功能；跨功能复用通过引用表达，不复制正文。
- 为项目、系统、功能、文档、章节、正文块、图示和附件分配稳定字符串 ID，优先沿用项目既有 ID；新增可用 UUID。不用标题、章节序号或数组下标作为身份。
- 规则、情况、玩家反馈、UI 页面和配置说明以正文块表达，块有 `blockId` 和 `subtype`。正文显示自然名称，ID 留在文件数据及 HTML 属性中。
- 改名、排序和移动保留 ID；复制为新对象生成新 ID；拆分或合并保留旧目标映射，无法一对一映射时提示旧链接所指内容已调整，不跳到无关段落。
- 同一案子的 HTML、JSON、导图和附件引用使用同一套 ID。文件名或标题相同不代表同一文档。
- 项目、系统资料未提供时对应归属可为 null，导入预览时绑定目标；不能为凑齐层级编造真实项目。文档及已定义功能仍有稳定 ID。

## 2. 交付形式与内容来源

交付 `功能名策划案.html`、同目录 `planning.json`，以及实际存在的图稿、配置和独立需求 Excel。可整体打包 ZIP；JSON 与包内链接均用相对路径。

导入前以 HTML 为维护入口。用语义化章节及正文块保留 `data-document-id`、`data-section-id`、`data-block-id`、`data-category`、`data-subtype`，并给正文块设置稳定 HTML 锚点。每段正文、表格、图示及附件引用都属于明确的块，不能只提取摘要而漏掉正文。

`planning.json` 是从同次保存的 HTML 正文、图示源数据和明确的业务关系导出的数据，不另行手写维护一套规则。结构化模型驱动 HTML 的生成流程也可使用，但两个输出必须来自同一份内容。HTML 的页内图示编辑影响导出数据时，保存应更新配套 JSON 或下载完整包；不得把只下载新 HTML 称为整包已同步。旧案局部修改无需强制整体转换；用户要求准备导入时再补齐标识和数据。

HTML 与 JSON 不一致时停止覆盖导入并报告差异；不能任意选一份当最新版。通过 HTML 文件的 SHA-256 校验值识别 JSON 是否对应该文件，同一版本号不能代替内容一致性检查。

## 3. `planning.json` 交换约定（v1）

| 字段 | 结构及用途 |
| --- | --- |
| format / schemaVersion | 固定 `game-feature-planning` / 整数 `1`；与工作台内部编辑器 schema 版本分别管理 |
| packageId / exportedAt | 本次导出包 ID / ISO 8601 时间；每次导出生成新 packageId，业务对象 ID 保持不变 |
| source | `{htmlPath, htmlSha256, maintenanceOwner, workbenchOrigin}`；maintenanceOwner 为 `html` 或 `workbench`，表示维护入口而非完成状态 |
| source.workbenchOrigin | 首次离线案为 null；工作台导出时为 `{workspaceId, projectId, documentId, baseRevision}`，用于定位来源和检查覆盖冲突，不能用该字段替代目标权限检查 |
| project / systems / features | project 为 `{id, name}` 或 null；systems 为 `{id, projectId, name}` 数组；features 为 `{id, systemId, name}` 数组；未知父级为 null |
| document | `{id, title, version, ownerType, ownerId, sections}`；ownerType 为 `system` 或 `feature`，ownerId 指向包内对象；version 是策划版本，不是数据库 revision |
| document.sections | 有序 `{id, title, categoryKey, blocks}` 数组；不按卡片分组重排原文 |
| blocks | 有序 `{id, title, subtype, anchor, contentHtml, references}` 数组；title 可为空，anchor 为不含 # 的 HTML 元素 ID；contentHtml 包含完整正文片段，不包含页面导航或交互脚本 |
| references | `{kind, targetId}` 数组，kind 为 `block`、`diagram`、`attachment`；引用包内对象，外部网页链接保留在正文中 |
| relations | `{id, fromId, toId, relationType}` 数组；业务对象或正文块之间的明确关系 |
| diagrams | `{id, kind, blockId, sourceFormat, sourceData}` 数组；kind 为 mindmap/flow/config/ui，保留节点、连线或可编辑 SVG 等源数据 |
| attachments | `{id, path, name, mediaType, role, sha256}` 数组；role 区分美术/UI/特效需求、配置、图稿、演示等；只列实际文件，不包含主 HTML 和 planning.json 自身 |

所有对象 ID 在包内唯一；所有引用必须可解析，未知父级的 null 除外。没有图示、附件或额外关系时使用空数组。`contentHtml` 是受限正文片段，导入器转换为编辑器块，不能直接执行；无法转换的内容须保留原件并报告，不能静默丢弃。

分类键统一为 `revisions`、`mindmap`、`description`、`config`、`ui`、`localization`、`audio`、`redpoint`、`analytics`、`attachments`、`unclassified`。对应正文十章；旧案无法归类的内容保留为 unclassified。

块子类型可用 `overview`、`rule`、`scenario`、`feedback`、`ui-page`、`config`、`resource`、`other`。卡片取块标题和正文摘要，并引用 sectionId/blockId；不能保存一份可独立修改的卡片正文。一个块可被多个视图引用，但只有一个原始位置。十章阅读顺序与卡片展示分组独立。

不生成 workflowStatus、fillStatus、完成度、缺项数量、审批、验收记录或待确认事项字段。版本、来源和技术保存信息不表示制作进度。规则不明确时在对应正文片段说明缺少的信息，不升级为管理对象。

## 4. 业务关系与图示

业务关系使用明确类型：`contains`（包含）、`depends_on`（依赖）、`triggers`（触发）、`references`（引用）。依赖方向为“依赖方 → 被依赖方”，触发方向为“触发来源 → 被触发对象”。情况与规则、UI 与反馈等用引用关联到具体块。

项目/系统/功能的归属是包含关系的唯一来源，工作台从归属生成这些 contains 边；relations 不重复存储这些边，避免两套归属冲突。其他关系仅保存资料中已明确的语义，不根据节点文字、相邻位置或普通连线猜测。

思维导图、流程图和配置图保留各自的节点/连线和布局；图示节点通过 `targetId` 引用业务对象或正文块。普通说明节点可没有 targetId，不能因此创建虚构功能。业务对象和图示节点 ID 分开，导图的拖动、排版或改显示文字不自动改业务规则或归属。

## 5. 导入与维护入口切换

1. 导入器读取包，校验格式版本、校验值、ID、引用及附件路径，展示完整正文和转换差异。首次导入时绑定真实项目/系统/功能，保留源 ID 到工作台 ID 的映射。
2. 提交正文、归属、显式关系和资源后，从正文生成卡片、目录与搜索索引；不把原 HTML 的任意脚本作为工作台组件执行。图示数据由工作台自己的图示组件读取。
3. 导入并开始编辑后，工作台数据库中的结构化正文成为维护入口；保留导入原件作为历史来源。随后导出的 HTML、JSON 和 Excel 是带版本的快照，不与原 HTML 双向自动同步。
4. 再次导入时按 documentId 和来源映射定位，不按文件名覆盖。同一目标、同一内容重复导入保持幂等；替换已有文档须有匹配的 baseRevision，并走预览与版本检查。缺少基线或版本冲突时比较差异，选择合并或作为新文档导入，不覆盖工作台新内容。
5. 复制到新项目时重新分配目标 ID 并重写包内引用，保留来源映射；同项目继续维护则沿用身份。整项目备份恢复与单篇策划案更新分开处理。

这些是导入和导出实现约定。工作台尚未开发时只验证文件结构和一致性，不宣称已在目标工作台成功导入。
