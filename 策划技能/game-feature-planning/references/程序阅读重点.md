# 程序阅读重点

策划案优先让研发判断功能边界、数据形状、计算过程与界面行为。物品名称、属性数值、技能名称等具体配置内容放在配置附件或折叠示例中；示例用于解释或验证规则，不替代规则，也不变成写死的数量、ID 或分支。制作需求表仍保留实际资源明细。

## 类型、数量与结构

分别说明业务类型和数据类型，例如“可叠加资源奖励”与 `Reward { resourceId: ID, count: int }`。当前功能只支持一种业务类型时直接说明，不为了通用性增加未要求的物品、属性、技能或礼包能力。

对每项配置和复合结构说明：单值、可空对象、固定长度数组、可变长列表或键值映射；元素/子字段类型；最少和最多多少个；空值、空列表、缺失字段的含义；顺序和重复规则。列表数量与每个元素内部的数量字段分开写。区分“配置列表有 N 项”“抽取 K 项”“每项固定数量/随机范围”三种数量，不从三条示例推断最多三项。

配置关系图标注 1:1、1:N、0..1 等实际基数；复杂子结构单独定义。ID 的引用类型和支持的业务范围应明确；未知枚举、越界、引用丢失给出具体结果。玩家已有数据和当前结果也可定义逻辑形状，但不因此编写接口协议、数据库或存储设计。

## 公式与判定

规则与公式以含义命名，引用使用可点击的名称，不要求读者记忆字母编号；稳定链接锚点只用于定位。

用参数化表达式描述计算，不只给某组数值的答案。定义输入变量、类型、单位、适用条件、计算顺序、输出、上限/下限、取整时点与方式、等号边界、异常输入。展示公式和实际判定/结算公式分开写。

按功能实际需要说明：概率归一化与随机区间；固定/随机数量；资源扣除与发放；时间周期；属性加成顺序、叠加和封顶；技能触发条件、次数与冷却。只覆盖当前功能，不机械增加无关公式。少量符号或边界算例用于证明语义，详细示例值放在配置附件。

## UI 的可实现表现

逐控件给出数据来源、显示文字/图标、显示/隐藏/禁用条件、点击后的结果与跳转。列表明确排序、行列、可见条数、滚动/分页、空状态、缺图、超长名称和数量格式；结果区明确是单项还是列表。

为正常、加载、空、锁定、处理中、结果不明、成功和失败等实际存在的状态定义优先级与切换，说明返回/关闭、重复点击、中断恢复和红点。动画写清开始条件、时长、可跳过范围、结束与打断结果；不能用“根据情况显示”“播放特效”等泛词代替行为。

不强制界面采用同一套布局或状态枚举；以本功能实际需要为准。已有项目适配、样式和组件规则优先，未经确定的视觉规格保持建议状态。

## 自查

将示例奖励换成同类型的另一组、将列表从 1 项改成多项：研发仍应能根据正文确定如何计算、如何排列、如何反馈，不需要额外猜测。公式做边界核对；表、图、原型和制作需求中不得残留与正文矛盾的固定数量或特定内容分支。
